1. Как начать

  1. Распаковать весь архив в одну папку. Открыть swagger.html: стили, скрипт и спецификация находятся локально; интернет для просмотра не нужен.
  2. Для живого просмотра фикстур запустить node mock-server.mjs, затем открыть http://localhost:5080/swagger.html. Этот mock обслуживает GET и возвращает контрольные данные. Запись, экспорт PDF и расчёт новых входных данных в нём не реализованы; он не подменяет backend.
  3. Backend: выполнить psql -v ON_ERROR_STOP=1 -d pilot_db -f schema.sql в пустой БД. Скрипт содержит собственную транзакцию. Повторное исполнение намеренно не идемпотентно: далее изменения идут миграциями.
  4. Использовать openapi.yaml или эквивалентный openapi.json как единственный контракт. Изменения полей, enum, статусов и ошибок одновременно обновляют файл и обе команды.

Дополнения после Figma: protocolNumber, laborPeriod, updatedAt, роли участников, productCode/фильтр полноты, объяснение каждой оценки, рабочие места вхождений, assignment-options и direct-selection-options. Приложение ASP.NET пока не создавалось. Версию .NET и пакетов закрепить при старте проекта, а не выводить из языков, упомянутых в исходном ТЗ. Принятые здесь PostgreSQL, Bearer-аутентификация и точные decimal-строки — решения архитектуры, не требования заказчика.

2. Модель данных

Открыть карту связей БД. В SQL — 13 таблиц и одно расчётное представление. Технический идентификатор везде UUID, имя не служит ключом. Реквизиты предприятия, ИНН, общий laborPeriod и выводы матриц хранятся в версии анализа: их изменение не переписывает прошлые документы.

ТаблицаНазначение и связи
analysisКорень анализа, owner_subject внешней аутентификации, дата создания. В базовом сценарии один оператор. Подписанты не пользователи приложения.

rule_setНеизменяемая версия правил. Нельзя редактировать веса и критерии через UI. Изменение методики означает новую запись/версию правил и новую миграцию, не UPDATE истории.
productНоменклатура: единица, продажи, выручка, именно сырьевая себестоимость, календарная длительность, ожидания, план, источники. null отличается от 0/false.
operation; product_route_stepСправочник операций с workplaceName и упорядоченные вхождения в маршрут продукта. RouteStep.workplaceName может переопределить место повторного вхождения. Повтор операции имеет отдельный occurrence_id. UNIQUE(product_id,position), не UNIQUE(product_id,operation_id).
family; family_productСемейство — кандидат-поток с границами, подтверждением и составом. product_id — PK таблицы членства, поэтому продукт входит максимум в одно семейство этой версии.
family_route_stepПодтверждённый маршрут потока, независимые вхождения и порядок. При изменении продуктового маршрута подтверждение связанного семейства сбрасывается.
family_metricsРост продаж, загрузка, тип производства, трудоёмкость и их периоды/основания. 1:1 с семейством. Расчётная маржинальность и доля выручки здесь не дублируются.
protocol; selection1:1 с версией: реквизиты документа и отдельно проект выбора. Сохранение выбора не фиксирует решение. Номер протокола хранится явно в protocol_number, отдельно от agreement_number. Для dominantProduct указан продукт.
decisionРовно одно решение на фиксированную версию: автор, время, полный типизированный snapshot, hash и версия правил. Снимок включает и исключённые потоки, их исходные данные и причины.
family_financials (view)Суммы семейств, известный максимум длительности, флаги неполноты и нарушения допуска. Не вычисляет рейтинг: тот принадлежит серверной предметной логике.

Составные FK (version_id,entity_id) запрещают связи между версиями. Источники Evidence и участники хранятся JSONB с формой, заданной OpenAPI; проверка содержимого выполняется ASP.NET. JSONB snapshot допустим для неизменяемого снимка, рабочие данные и связи нормализованы. Индексы покрывают владельца анализа, списки версии, членство и обратные ссылки на операции.

PK/внешние ключи/ограничения/триггеры находятся в SQL. Сервер проверяет непрерывность position=1..N, соответствие маршрутов, длину полей, диапазоны Evidence, полноту и все бизнес-правила. Для route и membership замена атомарна. При delete семейства с продуктами или использованной операции — 409; сначала явно убрать/перенести связи.

3. HTTP и типы

АспектКонтракт
Адрес и формат/api/v1; JSON camelCase; UUID; даты YYYY-MM-DD; UTC timestamp с Z. Валюта RUB, деньги в рублях (не млн рублей). При импорте Excel будущая реализация умножает млн на 1 000 000.
Точные числаВ HTTP decimal — строка с точкой без экспоненты/разделителей; в C# decimal; в SQL numeric(24,6). До 18 целых и 6 дробных знаков. Количества/проценты/часы тоже строки. Баллы «1.5», загрузка «50». UUID/дата/число никогда не выводятся локализованными.
ОкруглениеВвод более 6 дробных знаков отклоняется, а не молча округляется PostgreSQL. Производные числа возвращаются до 6 знаков, MidpointRounding.AwayFromZero; UI может показать 1–2. Допуск и ранги вычисляются до округления. Для сравнения отношений использовать точные рациональные сравнения (масштабированные BigInteger числители/знаменатели), чтобы равные округлённые доли не стали равными местами. Переполнение формата ответа — 422 NUMERIC_RANGE, без усечения.
ЧерновикиВсе ключи DTO передаются; неизвестные nullable-поля — null. PUT полностью заменяет вводимые поля, не PATCH. Отсутствующий обязательный ключ — 400. Неполнота разрешена; невалидный формат/отрицательная выручка — нет. Пропуск показателя требует причины к проверке готовности.
КонкурентностьВсе изменения вложенной версии требуют If-Match с ETag всего агрегата. Пример "v:00000000-0000-4000-8000-000000000011:r:1". Любая успешная запись повышает revision и возвращает новый ETag. Клиент после 412 перечитывает версию и предлагает восстановить правки; автоматический повтор с новым ETag запрещён.
ПраваBackend берёт subject из проверенного Bearer-токена, не из тела. Каждый запрос проверяет владельца и всю цепочку analysis/version/entity. Чужие ID дают 404. Для dev допустим фиксированный локальный оператор только в Development. Выдача ролей, приглашения и логин собственного провайдера не входят в пакет.
Ошибкиapplication/problem+json; code, traceId и issues с JSON Pointer, сообщением и способом исправления. 400 формат; 401 вход; 404 ресурс/доступ; 409 состояние/зависимость; 412 revision; 422 бизнес-валидация; 428 нет If-Match.
Спискиoffset/limit (по умолчанию 100, максимум 1000), total (после фильтра), unfilteredTotal (до фильтра), q; для продукции — completeness=all/complete/incomplete и поиск по productCode. Для products/operations/families — name,id; анализы/решения — createdAt,id; версии — versionNumber. q для версий применяется к title, для решений — имени выбранного потока из snapshot. Чтение одного ответа — согласованный снимок одной revision; страницы разных revisions клиент перечитывает.

Ответы со списками анализов/версий/решений и /me,/rules не имеют единого изменяемого агрегата: ETag там можно не выдавать. ETag decision/exportDecision неизменяемый на основе snapshotSha256. Для всех GET вложенной версии ETag обязателен. Для POST /analyses возвращается ETag созданной версии. DELETE возвращает 204 с ETag без тела.

4. Расчёт — обязательный порядок

  1. Проверить исходные данные. Финансовый период 12 полных календарных месяцев перед projectStartDate; трудовой — последние 6 полных месяцев перед этой датой. Это принятое уточнение слова «последние», не утверждённый факт методики. Все источники содержат source и period либо assessedOn. analysis.laborPeriod хранит общий период труда, laborEvidence.period каждого потока должен ему соответствовать. Финансовые данные относятся к financialPeriod, план к activitiesPeriod, рост к forecastPeriod. Разные основания учёта и валюты не смешиваются.
  2. Сверить выручку. Суммировать каждый продукт один раз, включая «Прочее». Если есть неизвестная выручка — сверка неизвестна. Если сумма выше totalRevenue — блокировать рекомендацию/полный комплект/фиксацию. Если меньше — нужны remainderExplanation или строка «Прочее»; объяснённый остаток разрешает обычный рейтинг, но не подтверждает полноту/доминирование. Неизвестные затраты остатка не ноль. totalRevenue должен быть >0 для расчёта долей.
  3. Подтвердить состав. Предложение семейства сравнивает последовательности (operationId, эффективное workplaceName), включая повторения. Пустой маршрут не основание группировки. Для полного сценария вся не-Other продукция распределена, семейства непустые, границы и маршруты подтверждены. Перенос/изменение маршрута снимает affected confirmed. При разных маршрутах автоматического объединения нет: специалист приводит подтверждённые маршруты/укрупнение с покрытием ≥80% и основанием.
  4. Посчитать финансы. revenue=sum(product.revenue); cost=sum(rawMaterialCost), только если все компоненты известны; marginIncome=revenue−cost; marginPercent=marginIncome/revenue×100 при revenue>0; share=revenue/totalRevenue×100. Маржинальности не усреднять. Объёмы разных единиц не суммировать.
  5. Допуск. share≥10%; для каждого члена days≤30 и inProductionPlan=true. Любое известное нарушение → excluded, одновременно показываются все известные нарушения и все пропуски. Без нарушения, но с пропусками → unknown. Полностью пройдено → admitted. Пустое семейство → unknown. Проверка maxDuration не скрывает неизвестные сроки отдельных позиций.
  6. Относительные критерии. Сравнивать admitted-потоки. Dense rank: 40,40,30 → 1,1,2. Неизвестное значение у admitted-потока делает относительный критерий других preliminary. Наличие unknown-допуска также делает весь рейтинг preliminary, так как состав сравнения ещё может измениться. Исключённые не влияют на ранги.
  7. Баллы и результат. Шесть критериев по таблице ниже. При пропусках — knownScoreSum и количество известных баллов; totalScore/rank=null, isProvisional=true. Частичная сумма может быть видна, но не становится окончательным рейтингом. Исключённым: шесть notApplicable, totalScore/rank=null. Относительные предварительные баллы можно показать, но статус complete запрещён.
  8. Выбор. Только подтверждённый допущенный поток. В ranked первый ранг не имеет порога 7; второй требует ≥7 и обоснование обстоятельства вне шести критериев; третий запрещён. Равные лидеры выбираются явно с обоснованием. Когда canRecommend=false, окончательная ranked-фиксация запрещена. Ошибка документа/пропуск подписи не мешает сохранить черновик.

Для сравнения одна согласованная laborUnitCode и база 1; штуки/тонны не приводятся простым пояснением. При несовместимости — preliminary до ручного обоснованного приведения к общей базе.

Оценка различия циклов: (max(sum(hours))−min(sum(hours)))/min(sum(hours))×100. Неизвестное время любого вхождения либо min=0 → проверка unknown с причиной. >20% — warning, не дополнительный недопуск; подтверждение требует compositionReason. Время оборудования, человеко-часы и календарная длительность — разные поля. Поле «Время операций» на карточке продукции в контракте — производное family-matrix.routeDurationHours; изменяется через маршрут, чтобы исключить два противоречащих источника.

5. Прямой выбор

monoproduct: nomenclatureComplete=true, источник полноты, единственное реальное подтверждённое семейство всего предприятия, отсутствует неизвестный остаток. Один введённый или один допущенный кандидат сам по себе условие не выполняет. dominantProduct: весь перечень продуктов известен, доля выбранного продукта строго >20%, его выручка ≥2×выручки любого другого продукта. Неизвестное «Прочее» блокирует доказательство. В этом контракте выбранное семейство должно содержать только dominantProductId: расширение границ на другие продукты не выводится из доминирования одного продукта. Это консервативное проектное решение.

Прямой выбор не требует шести оценок/места, но требует допуска, полного протокола и исходных данных, необходимых для печати доли, маржинального дохода и прогноза. В приложении выводятся доступные обе матрицы и причина неприменения рейтинга; пустые баллы печатаются как «не применялось». Печать не означает утверждение. В Figma (экраны 36–37) состав приложений прямого выбора оставлен несогласованным. Для реализации принят вариант: обе матрицы включаются с отметкой «рейтинг не применялся»; это проектное решение, которое можно изменить отдельной версией правил.

6. Жизненный цикл и транзакции

POST /analyses → draft v1
PUT ввод / маршруты / состав / показатели → revision + 1
GET evaluation → пересчёт всего согласованного агрегата
PUT protocol → реквизиты; PUT selection → проект выбора
GET validation / protocol-preview → issues и данные трёх частей
GET export?draft=true → неполный документ «ЧЕРНОВИК»
POST finalize → неизменяемый Decision + fixed
POST fork → новый draft v2, старый Decision неизменен

Все изменения используют одну транзакцию и блокировку корня версии. Сначала авторизация и CAS (ожидаемая revision), затем изменения и инвалидация связанных данных. При изменении состава семейства его ручные family_metrics сбрасываются в null/unknown, причины указывают COMPOSITION_CHANGED; нельзя переносить показатели прежнего состава на новый. Для изменения маршрута аналогично сбрасываются трудоёмкость/загрузка затронутого семейства до подтверждения актуальности. При изменении AnalysisInput, продукции, операций, маршрутов, состава или metrics удаляется selection; при сохранении protocol/selection выбор не сбрасывается. Ни одна операция не записывает чужие/перемещённые между версиями UUID. В SQL пример CAS дан после миграции; корневое изменение revision должно быть единственным в транзакции.

Finalize: блокировка версии → проверка If-Match → повторный расчёт → проверка полноты, правил, выбора, managerDecisionReference и реквизитов → создание снимка со state=fixed и итоговой revision → вставка decision → перевод корня в fixed → COMMIT. Для этой команды изменение корня выполняется один раз в конце (revision+1); блокировка в начале SELECT FOR UPDATE. Deferred-триггеры проверяют пару decision/fixed на commit. Поля snapshot и hash валидирует приложение, триггер не заменяет предметную логику. SHA-256 считается по каноническому UTF-8 JSON RFC 8785 всего snapshot. Decimal-строки канонизируются перед созданием snapshot единообразно (без лишних нулей). Snapshot.evaluation.revision и familyMatrix.revision равны финальной revision. createdBySubject и createdByName берутся из проверенной сервером личности.

Повтор запроса: первая фиксация 201, новая фиксация fixed-версии 409 (либо 412, если сервер сначала проверил старый ETag). Внутри одной версии UNIQUE(version_id) не допускает дубля. После сетевой ошибки клиент читает список решений. Fork копирует все данные и связи в новые UUID, сбрасывает selection, сохраняет реквизиты с protocolDate=null, переводит подтверждения семейств в false, сохраняет rulesVersion, номер версии +1. Если уже есть draft — 409. Переход версии правил в этом API не предусмотрен.

SQL-триггеры защищают fixed-данные и историю. CAS обеспечивает сервис. Прямые записи в БД мимо сервиса нарушают revision-контракт и не поддерживаются. Приложение работает отдельной ролью без DDL/TRUNCATE, не владельцем БД; owner-фильтр обязателен во всех запросах. Аутентификация и CORS настраиваются в будущем ASP.NET проекте.

Фронт не рассчитывает допуск, ранги и возможность окончательного выбора. Он показывает серверные issues и canSelect/canFinalize. Backend не привязывает доменную модель к названиям UI-компонентов. Экраны сопоставлены с Figma; соответствия 01–41 перечислены в figma-api-map.csv.

Первый вертикальный этап — готовые кандидаты с обязательным списком входящих продуктов и допуском каждого продукта. Для этого не нужен второй несовместимый DTO: products + families + metrics используются с начала. Полный сценарий позже добавляет маршруты, подтверждение состава и матрицы. Раннее неполное состояние всегда draft; финализация полного сценария требует всех данных.

Вне базового контракта: XLSM-import, роли/приглашения/согласования, задачи, обходы, календарь, 1С, электронная подпись и графический редактор. История фиксированных решений включена для неизменяемости, полноценный аудит каждого редактирования — нет. Если импорт добавят, только предпросмотр листа 4.1, никаких макросов/готовых баллов/связей по строкам 5.1.
