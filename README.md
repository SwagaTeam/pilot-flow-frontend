# Pilot Flow — Frontend

Angular 22, standalone-компоненты, TypeScript, SCSS. [Backend ASP.NET Core](https://github.com/SwagaTeam/pilot-flow-backend).

Сборка настроена через Angular CLI в `angular.json`: dev-сервер использует Vite, production-сборка — esbuild и Angular compiler. Отдельный `vite.config.ts` этому стандартному Angular builder не нужен.

## Запуск

Нужен Node.js `^22.22.3`, `^24.15.0` или `^26.0.0`.

```powershell
cd C:\Users\Evgen\Desktop\pilot-flow-frontend
npm ci
npm start
```

Открыть [http://127.0.0.1:4200](http://127.0.0.1:4200).
По умолчанию открывается явно обозначенный учебный анализ. Для него не нужны бэкенд, БД или токен.
Данные взяты из существующего контракта; сохранение и PDF в этом режиме отключены. Ввод в формы не меняет фикстуры.

## Подключение бэкенда

1. Запустить соседний `pilot-flow-backend` с PostgreSQL, применёнными миграциями и настройками JWT по его README.
2. Проверить `http://localhost:5037/health/ready`.
3. Во frontend открыть **Учебные данные → Анализы и подключение**.
4. Ввести действующий Bearer JWT с claim `sub`, получить список анализов и открыть существующий либо создать новый.

`proxy.conf.json` направляет `/api/**` и `/health/**` на `http://localhost:5037`.
Для Docker на порту 8080 заменить `target` на `http://localhost:8080` и перезапустить `npm start`.
Токен хранится только в памяти вкладки; после перезагрузки нужно подключиться повторно. Учебные данные никогда не подставляются вместо ошибки рабочего API.

В production сервер должен отдавать `dist/pilot-flow/browser`, перенаправлять неизвестные пути интерфейса на `index.html` и проксировать `/api/v1` в ASP.NET Core. Dev-прокси не включается в production-сборку. Авторизацию и БД настраивает бэкенд; frontend их не обходит.

## Реализованные разделы

- Подготовка анализа: предприятие, периоды, источники, участники.
- Продукция: поиск, фильтр полноты, добавление и редактирование, неизвестные показатели.
- Маршруты: справочник операций, последовательность, повторные вхождения, рабочие места и длительность.
- Семейства: состав, границы, подтверждение, назначение продукции, создание отдельного семейства.
- Допуск и сравнение: серверные результаты, предварительный рейтинг, объяснения каждой оценки.
- Решение: выбор по рейтингу, обоснование второго места, проверка прямого выбора.
- Документы: реквизиты протокола, матрицы, серверная выгрузка PDF, фиксация решения, просмотр сохранённого комплекта и новый черновик.
- Состояния загрузки, пустых списков, ошибок API, отсутствующих значений и конфликта ревизий.

Расчётные значения, совместимость, ранг и возможность фиксации определяет API. `null` не превращается в ноль. Decimal-поля передаются строками; форматирование не использует `Number` для денежных данных. Формы сохраняют ETag прочитанной версии и передают его в `If-Match`. После `412` запись не повторяется автоматически: исходный ввод остаётся на экране для сверки, затем можно перечитать анализ.

Списки загружаются до 1000 записей на каталог; если сервер вернул больше, показана явная ошибка, а не неполный расчёт. Серверная пагинация для каталогов большего размера — дальнейшее расширение. Удаление сущностей и полный редактор всех полей Evidence не входят в стартовую интеграцию.

## Макеты

[Исходная Figma, экран назначения продукции](https://www.figma.com/design/laHj7WJpCBLjxP4ODyuybk/?node-id=10-1369).
`figma-api-map.csv` содержит исходную карту 41 экрана/состояния. Основные состояния объединены в маршруты приложения, а не продублированы отдельными статичными страницами.

Текущая вёрстка — рабочая первоначальная реализация. Через публичный просмотр проверены общая компоновка, подготовка анализа и назначение продукции. Figma API отказал в чтении слоёв из-за отсутствия прав редактора у подключённого аккаунта. Поэтому полная сверка всех 41 состояний, точных шрифтов, отступов и токенов ещё не завершена; пиксельное соответствие не заявляется.

## Проверки

```powershell
npm run build
npm test
npm run format:check
```

Тесты проверяют маршруты с контрактными данными, HTTP-аутентификацию и `If-Match`, отсутствие повторной записи после 412, запрет записи в деморежиме, неизменность фикстур и точность представления decimal-строк.
Для проверки реального сохранения и PDF нужен запущенный API с PostgreSQL и действующий JWT. При первоначальной разработке API на портах 5037/8080 не был доступен; сквозной тест с реальной БД не выполнялся.

## Структура

- `src/app/core` — API-клиент, загрузка согласованной ревизии (`analysis-reader.ts`), состояние анализа, типы контракта, учебный адаптер.
- `src/app/pages` — страницы рабочего процесса: логика в `.ts`, большие шаблоны в отдельных `.html`.
- `src/app/shared` — общие элементы и форматирование.
- `src/styles.scss` — точка входа стилей; базовые правила, компоновка, компоненты и адаптивные стили разделены в `src/styles/`.
- `scripts/generate-contract.mjs` — генерация 51 DTO и read-only фикстур из `openapi.json`.

После согласованного обновления контракта:

```powershell
npm run generate:contract
npm test
npm run build
```

`openapi.yaml` и `openapi.json` — копия контракта backend 1.0.0: 45 операций, 51 схема. Их нельзя менять независимо от бэкенда.

Исходные `handoff.html`, `control-example.json`, `acceptance-vectors.json`, Swagger и `mock-server.mjs` сохранены. Старый read-only mock запускается командой `npm run mock` на порту 5080 и не требуется для нового встроенного учебного режима.
